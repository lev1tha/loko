# Loko + Kargo Osh → одна система: «один бэкенд, два лица»

**Решение (утверждено):**

- **Один бэкенд — Django Loko** (PostgreSQL): единый источник правды для клиентов,
  заказов, финансов и отчётности. Финансовый движок Loko (`reports.py`) НЕ переписывается.
- **Два лица по аудитории — одна система:**
  - **`lokobooking.com`** — рабочее место сотрудников и управленца (существующий
    React-SPA + админка). Персонал работает **только здесь, один URL** — без переходов
    между системами.
  - **`kargoosh.kg`** — публичное лицо для клиентов и поисковика; SEO/ЧПУ сохраняются.
    Остаётся сайтом, но слой данных переключается на **API Loko**.
- **Данные Kargo Osh** (клиенты, заказы, кассы, транзакции, регионы) **мигрируют в Loko**
  идемпотентным импортёром со сверкой «до копейки». PHP-админка Kargo после переноса
  выводится; операции региона Ош переезжают в приложение Loko.

**Почему так, а не «всё в Kargo»:** обе системы живые и владеют РАЗНЫМ — Kargo держит
клиентов + SEO, Loko держит финансы. Объединяем не по бренду, а «по проводам». Финмодель
Loko богаче (начисление/оплата, курсы-снапшоты, налоги по каналам, депозиты), модель
Kargo проще; **богатую модель нельзя схлопнуть в простую без потери данных** — значит ядро
обязано быть на богатой стороне (Loko), а лицо клиента/бренд (`kargoosh.kg`) остаётся.
Внешне это всё равно «одна система, kargoosh для клиентов, lokobooking для сотрудников».

## Целевая архитектура

```
   Клиенты + SEO ──▶  kargoosh.kg (публичный сайт)  ─┐
                      регистрация · трекинг · цены    │
                                                      │  HTTP / JSON
                                                      ├─▶  API Loko (DRF + JWT)
   Сотрудники   ──▶  lokobooking.com (ERP · SPA)   ─┘         │
   + управленец      заказы · склад · финансы · отчёты        ▼
                                                        PostgreSQL — единая база
```

Один бэкенд, одна база, два домена. «Туда-сюда» ходить некому: у каждой аудитории свой
вход, данные общие. Дисциплина миграции — та же «до копейки», что уже применялась для
импорта Business.

## 1. Что переносим — инвентарь Kargo Osh (MySQL)

| Таблица | Смысл | Переносим? |
|---|---|---|
| `user` | клиенты (код, телефон, регион, скидка, авторизация, Telegram) | **да** → ядро |
| `orders` | заказы (трек, вес, цена, статус, даты, админ) | **да** → ядро |
| `orders_unknown` | неопознанные заказы (пришли на склад без кода) | **да** |
| `cards` | денежные счета/кассы (баланс, валюта, kargo/business) | **да** → финансы |
| `transactions` | финансовый журнал (сумма, курс, дебет/кредит/перевод) | **да** → финансы |
| `admin` | сотрудники по регионам | **да** → пользователи |
| `template_users` | аналитика посещений | опционально (не ядро) |
| `slider`, `popular_products`, `params` | контент витрины | **нет** (остаётся на сайте) |
| `Rewrite` (ЧПУ) | SEO-URL | **нет**, но сохранить для редиректов |
| `OrderTezbiznes` | вторая линия «ТезБизнес» | **да, если активна** → Loko Business |

Легенда полей Kargo (OSClass-стиль): `pk_i_*` = PK, `fk_i_*` = FK, `s_*` = строка,
`i_*` = число, `dt_*` = дата/время, `b_*` = флаг.

### 2.4 `transactions` → `finance.Expense` / `Transfer` / `OtherIncome`

Kargo — карточно-центричный журнал; Loko — типизированный. Правила:

| Kargo `i_operation_type` | Loko | Примечание |
|---|---|---|
| `0` CREDIT (списание) | `Expense` (счёт=card, сумма, филиал, дата, коммент) | |
| `1` DEBET (пополнение) | `OtherIncome` / финансовый приток | |
| `2/3` TRANSFER (получен/отправлен) | `Transfer` (from/to card, `rate`=`i_transfer_rate`) | мультивалюта = как у Loko |

`i_transaction_type`: `1` оплата карго / `3` оплата ТезБизнес / `2` перевод.
⚠️ Оплаты за заказ (`PAY_FOR_KARGO_ORDER`, связаны через `orders.fk_i_transaction_id`)
не задваивать: выручка живёт на `Sale.paid_som`, транзакция — это факт оплаты в кассу.
Решить на этапе маппинга: либо транзакции-оплаты становятся `Sale.paid_som/payment_date`,
либо отдельным притоком — но **не оба сразу**. Сверять по суммам (§6).

## 4. Расширения схемы Loko (миграции Django)

Чтобы **ни одно поле Kargo не потерялось**:
- `express.Client`: `+ code, last_name, email, branch(FK), discount, tg_id, enabled, reg_date, legacy_kargo_id (unique, null)`; опц. блок авторизации клиента.
- `express.Sale` (или `WarehouseItem`): `+ tracking_number, dt_shipment, legacy_kargo_id (unique, null)`.
- `finance.Account`: `+ legacy_kargo_card_id (unique, null)`.
- `finance.Expense/Transfer/OtherIncome`: `+ legacy_kargo_id (unique, null)` для идемпотентности.
- `finance.Branch`: заведение регионов Ош.
- (опц.) `express` модель для ТезБизнес → или через Loko Business.

Поля `legacy_kargo_*` — обязательны: они дают **идемпотентность** (повторный импорт
не плодит дубли) и **прослеживаемость** (каждую строку Loko можно сверить с источником).

## 5. Гарантия «без потери данных» — метод

1. **Полный дамп MySQL** Kargo Osh (`mysqldump`) как неизменяемый бэкап. Это и есть
   страховка: миграцию можно перезапускать сколько угодно раз.
2. **Kargo переводится в read-only** на время миграции (стоп записи → консистентный срез).
3. **Идемпотентный импортёр** — Django management command (по образцу `import_business`):
   удаляет+пересоздаёт только свои строки (по namespace `legacy_kargo_*`), гоняется до
   сходимости. `--dry-run` печатает, что будет сделано, без записи.
4. **Баланс касс (§2.3)**: не переносить `i_amount` вслепую. Вариант А — `initial_balance`
   = баланс на дату начала журнала, затем транзакции реконструируют текущий (Loko-стиль);
   вариант Б — `initial_balance` = текущий `i_amount`, транзакции — только история.
   Выбор фиксируем так, чтобы **вычисленный Loko баланс == `cards.i_amount`**.
5. **Дедуп** по каноническому телефону/коду (Ош vs Бишкек — вероятно почти не
   пересекаются, но проверяем; при коллизии — правило слияния).
6. **Поэтапное переключение**: импорт → сверка (§6) → параллельная работа/чтение →
   переключение витрины на API Loko → вывод PHP-бэкенда.

## 6. Гейты сверки (числа обязаны совпасть с источником)

Импорт считается успешным, только когда всё сходится:
- `COUNT`: users, orders (по статусам 1/2/3), transactions, cards, admins.
- Σ `orders.i_price` — всего и по статусам; Σ `orders.i_weight`.
- Σ `cards.i_amount` (сумма балансов касс) == сумма вычисленных остатков Account в Loko.
- Σ `transactions.i_amount` по `i_operation_type` и по `i_transaction_type`.
- Дебиторка (начислено − оплачено) на обеих сторонах.
- Кол-во клиентов после дедупа = уникальные телефоны/коды источника.

Отчёт сверки печатает импортёр (`--report`); расхождения — блокер переключения.

### 6.1 Базовые числа (факт из дампа `user143204_kargoosh`, 28 МБ)

Импорт в Loko обязан воспроизвести эти значения:

| Сущность | Значение |
|---|---|
| Клиенты (`user`) | **9 613** |
| Заказы (`orders`) | **171 449** (в пути 13 120 · прибыло 4 303 · выдано 154 026) |
| Σ вес заказов | **154 922.62 кг** |
| Σ выручка `i_price` | **245 272 547.41 сом** (прибыло 508 000.61 + выдано 244 764 546.80) |
| Уникальных кодов клиента в заказах | 5 039 |
| Транзакции | **42 197** |
| Кассы (`cards`) | 8: карго **226 358 094.68 сом**, business **7 658 525.00 сом** + **9 563.80 ¥** |
| Транзакции — оплаты карго (tt=1) | 42 130 шт, +228 235 365.18 сом |
| ТезБизнес (`orders_tez_biznes`) | **36** (почти не используется — решить: мапить или заморозить) |

Найдено в структуре:
- Пароли клиентов — **bcrypt** (`char(60)`) → логины МОЖНО сохранить (Django-хешер bcrypt), без сброса.
- `orders.s_tracking_number`, `user.s_code/s_phone/s_email` — **UNIQUE** → чистые ключи дедупа/идемпотентности.
- Заказы статуса 1 («в пути») — без цены/веса → переносим как складские позиции **без финансовой продажи** (двухэтапная модель Loko); выручку несут только статусы 2/3.
- Масштаб 171k заказов → импортёр на **bulk-вставках**, с **сохранением исторической цены** (НЕ пересчитывать через `Sale.save()` — иначе перезатрёт прошлые суммы).
- Контент витрины (`pages/slider/popular_products/locale/settings/salawat_counter`) — в ядро не тянем.

## 7. Два фронта на одном API + SEO

### 7.1 `lokobooking.com` — рабочее место сотрудников (один URL)
Существующее приложение Loko (React-SPA + Django-админка) становится **единственным**
местом работы персонала. Сюда переносим операции, которые были в PHP-админке Kargo, чтобы
сотрудники Ош не открывали второй сайт: управление клиентами/заказами/ценами по региону,
неопознанные заказы, кассы/транзакции (уже финансы Loko), выдача. Роли Loko
(ADMIN/MANAGER/OPERATOR/WAREHOUSE/DIRECTOR) распространяем на регион Ош через `Branch`.

### 7.2 `kargoosh.kg` — публичное лицо клиента, на API Loko
Сайт остаётся (SEO — причина его существования: модель `Rewrite`/ЧПУ), но слой данных
переключается на API Loko:
- Существующие публичные эндпоинты: `/api/public/branches`, `/api/public/track`,
  `/api/public/intake`, `/api/public/rate`.
- **Добавить в Loko недостающие публичные эндпоинты** под нужды витрины:
  регистрация клиента, вход клиента (если сохраняем логины), тарифы/цены по региону,
  трекинг по трек-номеру, (опц.) популярные товары/контент.
- SEO не потерять: карту ЧПУ сохранить, со старых URL — **301-редиректы**;
  `sitemap.xml`/`robots.txt`/метаданные перенести.
- Контент витрины (`slider`/`popular_products`/`params`) остаётся на стороне сайта —
  в ядро Loko не тянем (это не учётные данные).

### 7.3 Авторизация клиента (открытый вопрос)
У Kargo клиент входит по логину/паролю; у Loko клиент — по телефону, без входа. Решить:
сохранить клиентские логины (тогда Loko выдаёт клиентские токены и хранит учётки) или
перевести клиентов на «вход по телефону». От этого зависит API п.7.2 и миграция `user`.

## 7.4 Переезд под домен kargoosh.kg (DNS + nginx)

Цель — всё под `kargoosh.kg`. Реализуется **поддоменами** (движок Loko остаётся на VPS:
на shared-хостинге hoster.kg — PHP 7.2 без постоянных процессов, Django там не поднять).
Клиентский сайт `kargoosh.kg` не трогаем — SEO цел.

Факты: `kargoosh.kg` → `176.126.165.192` (hoster.kg, nginx+PHP 7.2), DNS у `ns9/ns10.hoster.kg`
(без Cloudflare). Loko VPS — `157.250.205.157`.

1. **DNS** (в `mira.hoster.kg` → DNS зоны `kargoosh.kg`) — две A-записи на VPS:
   `panel  A  157.250.205.157` и `api  A  157.250.205.157`
   (`@`/`www` не трогаем — остаются на `176.126.165.192`).
2. **nginx на VPS**: `infra/nginx/{panel,api}.kargoosh.kg.conf` → `sites-available` → `sites-enabled`.
3. **TLS** (DNS прямой, без CF): `certbot --nginx -d api.kargoosh.kg -d panel.kargoosh.kg --redirect`.
4. **Сборка SPA** под этот API: `VITE_API_BASE_URL=https://api.kargoosh.kg/api WEB_DIR=/srv/www/kargoosh-panel …`.
5. **Loko settings** (`infra/.env` на VPS): `ALLOWED_HOSTS`/`CORS`/`CSRF` + поддомены (см. `.env.example`).
6. **Позже**: `lokobooking.com` → 301-редирект на `panel.kargoosh.kg` (когда всё проверено).

Итог: `panel.kargoosh.kg` — сотрудники, `api.kargoosh.kg` — API, `kargoosh.kg` — клиенты. Всё под одним доменом.

## 8. Порядок работ (поэтапно, без «взрыва»)

**Этап 1 — единая база (данные под одним ядром):**
1. Дамп MySQL Kargo + инвентарь значений (регионы, статусы, валюты, объёмы).
2. Миграции схемы Loko (§4) + карта регионов→Branch (§3).
3. Импортёр `import_kargoosh` — по слоям: Branch/User → Account(cards) → Client(user)
   → Sale/WarehouseItem(orders) → finance(transactions) → orders_unknown → ТезБизнес.
4. `--dry-run` + отчёт сверки (§6) → доводка до сходимости.
5. Дедуп-проход (телефон/код) + разбор коллизий Ош↔Бишкек.

**Этап 2 — клиентское лицо на API Loko:**
6. Добавить недостающие публичные эндпоинты (§7.2): регистрация/вход клиента, тарифы, трекинг.
7. Переключить страницы `kargoosh.kg` на API Loko + 301-редиректы, сохранить SEO/ЧПУ (§7).

**Этап 3 — единое рабочее место сотрудников:**
8. Перенести операции Ош из PHP-админки в приложение Loko (§7.1); раздать роли по региону.
9. Kargo-админку и PHP-бэкенд перевести в read-only → архив → вывод. Сотрудники — только
   на `lokobooking.com`.

После этапа 1 бизнес уже работает на одной базе; этапы 2–3 убирают второй интерфейс
постепенно, без остановки.

## 10. Риски

- Финансы (`transactions`/`cards`) — самый тонкий слой: разные модели учёта (карточная vs
  типизированная). Митигируется сверкой сумм по типам (§6) и выбором схемы баланса (§5.4).
